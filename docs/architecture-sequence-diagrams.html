1. 티켓 실행 — 드래그 → In Progress (헤드라인 플로우)

tickets.transition → _maybe_auto_dispatch → navigator → runs → [worker] → [watcher]
드래그 한 번이 3단계로 분리 실행됩니다: (A) API가 상태 전환 + 큐 적재(동기) → (B) worker가 큐를 집어 실행 → (C) watcher가 완료 감지 후 Reviewing으로 이동. A 직후의 UI 스냅샷에는 큐가 queued로 찍히지만, B·C는 백그라운드라 UI가 새로고침해야 done이 반영됩니다.

block.digest_policy==agent_execute & 활성 run 없음 API->>NAV: recommend(ticket) NAV->>DB: NavigatorDecision insert · assignee_persona 설정 API->>RUNS: create_run(persona/agent/model/skills) RUNS->>DB: AgentRun(status=queued) + QueueItem(state=queued) insert API-->>UI: TransitionResult (ticket=In Progress) Note over UI: 이 시점 큐 스냅샷 = "queued" (worker 아직 tick 전) Note over WK,WIKI: (B) 비동기 — worker_loop 3초 폴링 WK->>DB: SELECT queue_items WHERE state='queued' WK->>DB: QueueItem.state='running', locked_by='worker' WK->>AD: execute_run(run) AD->>LC: (필요 시) In Progress 전환 AD->>DB: run.status='running', started_at AD->>WIKI: result.md + .agent_done.json 작성 (sim) Note right of AD: real 모드 → CLI 서브프로세스 spawn,
CLI가 sentinel 작성 Note over WT,WIKI: (C) 비동기 — watcher_loop 2초 폴링 WT->>DB: SELECT runs WHERE status='running' WT->>WIKI: .agent_done.json 읽기 WT->>DB: Artifact + WatcherEvent insert WT->>DB: run.status='success', finished_at · QueueItem.state='done' WT->>LC: transition In Progress→Reviewing LC->>WIKI: raw 이벤트 + WikiSyncJob Kay->>UI: 새로고침 (or 보드 재진입) UI->>API: GET /queue · GET board · GET tickets API-->>UI: queue=done · ticket=Reviewing · run=success

2. Navigator 라우팅 (내부 동작)

services/navigator.py · recommend()
규칙 우선(rule-first) 라우터. 티켓 컨텍스트를 페르소나 키워드로 스코어링 → 최고 페르소나의 기본 agent/model 매핑 → 페르소나 호환성+태그로 스킬 랭킹 → RAG로 위키 컨텍스트 주입. task_kind와 manual override를 반영해 NavigatorDecision으로 기록.
sequenceDiagram autonumber participant API participant NAV as navigator participant RAG as rag participant DB as Postgres API->>NAV: recommend(ticket, override?, task_kind) NAV->>NAV: _context(ticket) — title+desc+AC+digestible comments NAV->>NAV: _score_personas() — 키워드 카운트 정렬 alt best_score == 0 NAV->>NAV: 기본 페르소나 = Full Stack Developer (confidence 0.40) else 키워드 매칭 NAV->>NAV: persona=최고점 · confidence = clamp(0.55 +0.07·hits +0.05·margin) end opt task_kind == "subdivide" NAV->>NAV: 기술 키워드면 CTO, 아니면 PM (planning persona) end opt override.persona/agent/model/skills NAV->>NAV: 수동 오버라이드 반영 (manual_override=true) end NAV->>DB: SELECT Persona → default_agent/model/family NAV->>DB: SELECT Skill → _recommend_skills() 랭킹 NAV->>RAG: search(context, k=3) — 위키 페이지 참조 RAG->>DB: WikiEmbedding 조회 NAV->>DB: NavigatorDecision insert + ticket.assignee_persona 설정 NAV-->>API: decision (persona·agent·model·skills·confidence·alternatives)

3. 서브디비전 — 에픽 분할

tickets.subdivide → subdivision.propose / approve
Kay가 분할을 트리거하면 Navigator가 기획 페르소나(CTO/PM)로 라우팅하고 자식 티켓 제안을 만듭니다. Kay 승인 시 자식들이 parent_ticket_id를 달고 Todo에 생성됩니다. 자식은 다시 분할 가능(재귀). 모든 자식이 Completed가 되면 부모가 자동 완료(롤업) — 리뷰 워크플로우에서 발생.
sequenceDiagram autonumber actor Kay participant UI participant API as API /tickets participant SUB as subdivision participant NAV as navigator participant DB as Postgres Kay->>UI: "Subdivide" ASV2-0012 UI->>API: POST /tickets/12/subdivide API->>SUB: propose(ticket) SUB->>NAV: recommend(task_kind="subdivide") NAV->>DB: NavigatorDecision(task_kind=subdivide, persona=CTO/PM) SUB->>SUB: _propose_children() — 프로젝트성이면 BE/FE/DB/Infra/Design,
아니면 Plan/Implement/Test SUB->>DB: SubdivisionProposal(status=proposed, children_json) insert API-->>UI: proposal (제안된 자식 목록) Kay->>UI: 제안 검토 후 "Approve" UI->>API: POST /subdivisions/{id}/approve API->>SUB: approve(proposal) loop 각 자식 spec SUB->>DB: Ticket(parent_ticket_id=12, status=Todo) insert end SUB->>DB: proposal.status='approved' API-->>UI: 생성된 자식 티켓들 (Todo) Note over Kay,DB: 이후 각 자식을 In Progress로 드래그 → 워크플로우 #1

4. 리뷰 / 리런 루프

tickets.review → review.review_ticket
티켓이 Reviewing일 때만 가능. 만족 → Completed + 부모 롤업 검사. 불만족 → In Progress로 되돌리고 리뷰 코멘트를 다음 run 프롬프트에 주입한 리런 생성 → worker/watcher가 다시 구동(워크플로우 #1로 회귀).

5. 취소 — run / queue item

runs.cancel_run · runs.cancel_queue_item
큐 항목 취소와 run 취소는 서로 동기화됩니다. real 모드에서 실행 중인 프로세스는 SIGTERM으로 종료 시도. 취소 시 티켓도 (종료 상태가 아니면) Canceled로 전환됩니다.
sequenceDiagram autonumber actor Kay participant UI participant API as API /runs|/queue participant LC as lifecycle participant OS as OS process participant DB as Postgres Kay->>UI: 큐 항목 / run 취소 alt 큐 항목 취소 UI->>API: POST /queue/{id}/cancel API->>DB: QueueItem.state='canceled', cancel_requested=true opt 연결된 run이 queued/running API->>API: _cancel_run(run) API->>DB: run.status='canceled', finished_at API->>LC: transition ticket→Canceled end else run 취소 UI->>API: POST /runs/{id}/cancel opt run.status=running & real process API->>OS: kill(pid, SIGTERM) end API->>DB: run.status='canceled' API->>LC: transition ticket→Canceled API->>DB: QueueItem.cancel_requested=true, state='canceled' end API-->>UI: 갱신된 run/queue

6. LangGraph orchestrate (대체 구동 경로)

tickets.orchestrate → orchestrator.run_ticket (StateGraph)
worker/watcher 폴링 대신 한 티켓을 명시적 상태그래프로 끝까지 구동: navigate → dispatch → (실패 분류) → watch → END. 내부적으로 같은 서비스(navigator/runs/adapter/watcher)를 호출합니다. 실패 분류에 따라 retry(최대 3) / rate_limited(재개 스케줄) / blocked 분기.
sequenceDiagram autonumber participant UI participant API as API /tickets participant OR as orchestrator participant NAV as navigator participant RUNS as runs participant AD as adapter participant FA as failure participant WT as watcher participant DB as Postgres UI->>API: POST /tickets/{id}/orchestrate API->>OR: run_ticket(id) (compile StateGraph) OR->>NAV: [navigate] recommend → persona/agent/model OR->>RUNS: [dispatch] 기존 queued run 재사용 or create_run OR->>AD: worker_tick(db) — 실행 OR->>FA: classify(run.error) → failure_cls alt USAGE_LIMIT OR->>FA: [rate_limited] schedule_rate_limit_resume(+5h) → END else TRANSIENT & retries<3 OR->>OR: [retry] retries+1 → dispatch 재진입 else TRANSIENT & retries>=3 OR->>DB: [blocked] transition ticket→Blocked → END else NONE OR->>WT: [watch] watcher_tick → Reviewing/Blocked → END end OR-->>API: state (ticket_id, run_id) API-->>UI: {status, run_id}

7. 부팅 복구 (durability)

main.lifespan → durability.recover_interrupted_runs
이 머신은 정전으로 WSL/컨테이너/tmux를 잃습니다. API 부팅 시 중단된 run(dispatched/running)을 찾아 queued로 되돌리고 큐를 재적재 → worker가 다시 집어갑니다(run은 멱등). 별도로 스케줄러가 Postgres 스냅샷을 /mnt/k로 덤프.
sequenceDiagram autonumber participant API as API (lifespan) participant SEED as seed participant DUR as durability participant DB as Postgres Note over API: 컨테이너 기동 API->>DB: init_db() — 테이블 생성 opt autoseed API->>SEED: seed_all() — 보드/페르소나/스킬 end API->>DUR: recover_interrupted_runs() DUR->>DB: SELECT runs WHERE status IN (dispatched, running) loop 중단된 각 run DUR->>DB: run.status='queued', process_id=null, started_at=null DUR->>DB: QueueItem 있으면 running→queued, 없으면 새로 insert end DUR-->>API: 재적재된 run 수 Note over API: yield → 정상 서빙 시작

8. 스케줄러 — LLM Wiki ingest/audit + 스냅샷

scheduler_loop.py · durability.create_snapshot
데일리 ingest(02:00 KST): pending WikiSyncJob을 ingested로 표시하고 raw 인덱스 갱신. 월말 audit(04:00 KST): raw 파일 존재/연결 검증. 스냅샷: pg_dump로 외부 디스크에 덤프 후 최근 N개만 보존.

10. 라이브 로그 스트림 (§13)

RunMonitor → /runs/{id}/stream (SSE) · /runs/{id}/log (폴링 폴백)
실행 중 run의 세션 로그를 실시간 tail. 1차는 SSE 스트림, 폴백은 byte-offset 폴링. real 모드에선 tmux pane을 같은 로그 파일로 파이프. run이 종료 상태가 되면 eof로 종료.
